# Swachh-Track Collector

Android-first Expo React Native app, package `@swachh/collector`. All implementation changes are confined to `apps/collector`. It extends the root strict TypeScript configuration and uses the root ESLint configuration (no explicit `any`). Root installation, package-manager setup and the shared lockfile remain the main build's responsibility.

## Run and Check

Run from the repository root after the main build installs the workspace dependencies with its pinned pnpm:

```sh
pnpm --filter @swachh/collector check:expo
pnpm --filter @swachh/collector typecheck
pnpm --filter @swachh/collector lint
pnpm --filter @swachh/collector test
pnpm --filter @swachh/collector start
```

Build/install the actual Android package with an Android SDK, JDK 17 and connected device:

```sh
pnpm --filter @swachh/collector android
```

The app ID is `in.swachhtrack.collector`. Native Android/iOS build directories are generated and ignored. Expo Go is useful for early development with a **compatible SDK 54 client**, but the Maestro flows target the installed native app ID, not Expo Go. Do not use an arbitrary newer Expo Go client and assume SDK 54 support.

`EXPO_PUBLIC_API_URL` defaults to `http://localhost:4000/api/v1`. Set it in the environment or `apps/collector/.env` using `.env.example`. For a USB-connected Android device:

```sh
adb reverse tcp:4000 tcp:4000
EXPO_PUBLIC_API_URL=http://localhost:4000/api/v1 pnpm --filter @swachh/collector start
```

For the Android emulator use `http://10.0.2.2:4000/api/v1`; for Wi-Fi devices use a reachable LAN address. **Presigned object-storage URLs must also be device-reachable**, not container hostnames. Forward the object-storage port separately if its signed URL uses localhost. Production API and object storage must use HTTPS; development cleartext networking is not a production security configuration. The public API URL is not a secret.

The main build now includes collector tests in the root Vitest suite. The package-local test command independently includes `src/*.test.ts`; this change did not modify root configuration. In the hosted build environment the pinned pnpm is available with `PATH=/tmp/bcode:$PATH`.

## Implemented Flow

1. Discover access using public `GET /api/v1/access`. For `open-demo`, load `/me` as `X-Demo-Role: collector`, select a valid collector membership automatically, and skip Login, sign-out and membership switching. For `authenticated`, retain phone OTP, SecureStore access/rotating refresh tokens, single-flight refresh on HTTP 401 and explicit `COLLECTOR` membership selection. Selected requests carry `X-Membership-Id`.
2. Register a stable SecureStore device UUID, generated by `expo-crypto`, using `{deviceId, platform:'android', appVersion:'0.1.0'}`. The returned active row must contain that same `deviceId` and `revokedAt: null`; its separate database `id` never replaces the bound UUID. First registration requires connectivity. Restored, registered sessions can capture offline. The API's `DEVICE_BOUND_OR_REVOKED` and `DEVICE_LIMIT` failures never generate a replacement UUID or mark registration successful.
3. Fetch today's ordered routes and cache them in SQLite under `userId:membershipId`. Stops show unit/block, ISO time windows, streams and last pickup. Dates are interpreted as Indian service dates; non-current caches cannot create new pickups. The actual API may return `qrToken: null` after QR rotation. That stop remains visible with an English/Hindi explanation and capture is blocked; other stops remain usable and the route can still be cached. Six-digit fallback preserves leading zeros and cannot bypass a missing/rotated QR.
4. Scan the exact signed QR with `CameraView`, or enter a six-digit code that uniquely matches the **selected stop in the selected cached route**. The fallback submits that stop's cached signed QR token. The client does not claim to verify HMAC signatures; the server does.
5. Capture a live doorstep photo and live scale photo for every scheduled stream. There is no gallery picker. Photos are re-encoded as JPEG at quality 0.65, resized to a maximum 1280-pixel long edge, copied into the app's documents/evidence directory, checked for existence, then referenced by a persisted draft. Original temporary photos are not uploaded.
6. Enter manually measured positive kg with at most three decimals, segregation, and contamination with a reason. All scheduled streams must be measured for a normal pickup. `ScaleAdapter` / `ManualScaleAdapter` expose the manual measurement seam; no Bluetooth hardware is simulated.
7. GPS is a fresh foreground position with latitude, longitude, accuracy and source timestamp. Location must be at most two minutes old when saving. Accuracy worse than 50 m is visible and left for server review rather than fabricated. No last-known fallback or continuous/background tracking is used.
8. Any listed exception requires identity, GPS, doorstep photo, note and an exception photo. An exception is submitted with `streams: []`, not fabricated `kg: 0`; it does not claim a partial weighed collection. `WEIGHT_UNAVAILABLE` is the default exception selection. All exceptions require supervisor review.
9. Save the immutable capture and photo records in one exclusive SQLite transaction; remove the draft in the same transaction. English/Hindi text uses typed translation keys, locale persists, and controls have at least 56-pixel tap targets.

### Discovered Open-Demo Access

No new `EXPO_PUBLIC` mode flag is used. The backend must expose `/access` with `{mode:'open-demo',roles:[{alias:'collector',role:'COLLECTOR'},...]}` only under its development/demo `NO_AUTH=true` gate, or `{mode:'authenticated',roles:[]}` otherwise. Backend gate enforcement belongs to the API, not this app. `/me` supplies the seeded collector identity and its existing `user`, `memberships`, `activeMembership` contract; the app does not fabricate a user or token.

Demo API requests always use `X-Demo-Role: collector`, omit Authorization/cookies, and add only the selected collector membership. Demo 401 responses do not refresh or call any auth endpoint. Presigned binary object-storage uploads remain separate capability requests without identity headers. Use **Retry startup** after a server access-mode change or bootstrap failure. The app never guesses that a failed discovery or demo bootstrap means Login should be shown.

SecureStore sessions are explicitly tagged `mode: 'open-demo'` or `mode: 'authenticated'`. Previously shipped untagged token sessions are read as authenticated sessions only. Demo sessions also bind the saved API URL, collector alias and stable device UUID. A separately persisted discovered-mode marker prevents a crash during a mode change from reviving an incompatible old session. Switching modes clears session credentials, not SQLite evidence or the device UUID; it does not copy authenticated registration state into demo identity.

On network errors/timeouts or HTTP 5xx, a valid saved session can restore offline. Demo restoration requires the same API URL/device, a valid selected collector membership and no token fields; cached registration is preserved only for that demo user/device/membership. An unregistered session still cannot collect until online registration succeeds. Explicit API denials and malformed responses fail startup with retry instead of silently falling back. A 401/403 from `/access` or bootstrap `/me` also deletes the saved session before failing, preventing offline retry or process reload from restoring the denied identity or its cached registration. The mode marker alone cannot authorize offline access. Online revalidation and device registration are required again; the device UUID is unchanged. Routes, drafts, events and photo checkpoints retain their existing `userId:membershipId` scope and are never deleted or migrated to another identity by session invalidation. First-ever offline boot requires a successful online discovery and `/me` first.

## Queue Guarantees

- SQLite uses WAL and full synchronous writes. Async writes are serialized and transaction work uses the exclusive transaction object, not the outer connection.
- Draft fields and photo references persist before the UI reports successful photo capture. A copied file left behind by a crash before the draft write is an orphan, not a falsely saved photo. Replaced/unreferenced files are conservatively retained.
- Events are scoped to user and membership. Sign-out does not erase queues, routes or evidence. Re-login to the same account/membership restores access. The device UUID remains stable across sign-outs.
- Each saved event has one immutable `client_uuid` and capture snapshot. SQL triggers prevent capture mutation and event deletion. Once all photo IDs are confirmed, a separate wire payload is written **once**, then reused byte-for-byte in every batch retry. Photo-ID materialization never changes the capture snapshot.
- Photo stages are `LOCAL -> PRESIGNED -> UPLOADED -> CONFIRMED`. Presign ID/URL, successful PUT and confirmation metadata are checkpointed separately. A restart after PUT retries confirmation first. A restart after server acceptance retries the same event UUID/idempotency key.
- Each photo uses presign `{kind, stream?, captureSource:'CAMERA', contentType:'image/jpeg'}`, binary JPEG PUT without JWT headers, then `/confirm`. Expired signed PUT URLs (400/401/403/410) are renewed and the new photo ID is checkpointed before re-upload. A confirmation response of **HTTP 422 with exact `error.code: 'UPLOAD_EXPIRED'`** also resets that unconfirmed photo durably to `LOCAL`, reserves again and uploads the same retained JPEG. Repeated explicit expiry is bounded per attempt and then backs off as `PENDING`, not `REJECTED`. A failed reset checkpoint prevents issuing a new reservation. Confirmed peers and immutable event/capture data never change; wire payload is frozen only after all confirmations succeed. Arbitrary 422 errors or expiry text without the exact code do not trigger renewal.
- API confirmation must be idempotent for a given photo ID. A lost response can require repeating confirmation; a lost presign response can leave an unused server-side reservation. Backend orphan cleanup remains a server concern.
- App startup recovers `SYNCING -> PENDING` without changing payloads or checkpoints. A module-level single-flight lock prevents overlapping automatic/manual sync runs and cross-membership sync overlap.
- Retry delays start at 5 seconds, double, and cap at one hour. Permanent transport errors require explicit retry. Automatic retries run when online and the app is foregrounded; no background-delivery guarantee is made.
- Single-event batches use `{events:[payload]}` and the event UUID as `Idempotency-Key`. Smaller sequential batches prioritize bounded memory and recovery on low-end phones, not a claimed 500-photo-event throughput target.
- `SYNCED` is transport acknowledgement, **not** the server verdict. `VERIFIED`, `NEEDS_REVIEW`, `REJECTED`, scores and reasons are displayed separately on stops and in diagnostics. Both top-level `results` and HTTP 422 nested `error.details.results` are parsed. A non-expiry 422 without a result remains visible as a hard rejection with the actual error, without inventing a server ID or score. Rejected records cannot be erased or silently resubmitted.
- Offline capture is sticky for the draft. Expected result: `NEEDS_REVIEW`, followed by explicit supervisor approval. The full prompt's offline-demo shortcut to immediate `VERIFIED` contradicts its verification rules; this app follows the rules and shows the actual server result.
- Local evidence is **never automatically deleted**, including after acknowledgement. This is deliberately conservative; approved retention/cleanup with a disk-space policy is a pilot follow-up, not an excuse to delete unacknowledged evidence.

## API Alignment

The collector was checked against `apps/api/src/auth.ts`, `pickups.ts`, `storage.ts` and the pagination helpers in `core.ts`. `/auth/refresh` accepts `{refreshToken}` and returns tokens plus user/memberships; `/auth/logout` accepts `{refreshToken}`. OTP verification includes `user.id` and memberships with `id` and `role`. Device registration, current-route JSON, confirmation metadata and explicit upload-expiry errors match these implementations. Contract tests use mocked HTTP/SecureStore; they are not a claim of native or live API end-to-end execution.

`GET /collector/sync/status` returns `{data:[...], nextCursor, rejectedSubmissions:[...]}`. Verdict refresh requests `limit=100`, follows the server cursor, and reconciles terminal local events by UUID, including supervisor approvals and rejected submissions. It loads the local queue once, parses each page once, uses constant-time UUID lookup, skips unchanged writes, deduplicates repeated rejected submissions, and stops when all local terminal events have been found or the cursor ends. It does not accumulate the server's full history in memory. Diagnostics show pages fetched, matches, updates, unmatched local events and the next cursor (if an early stop left unrelated history unread).

Completed updates remain in SQLite if a later page fails. Retrying starts at page one but skips unchanged results; the UI reloads even after partial failure. Malformed pages and repeated cursors fail visibly rather than looping or clearing records. Pending uploads, events in another local membership, and unmatched local rejections are not changed by verdict refresh.

The API returns only the latest 100 rejected submissions, repeated on every page; older local rejections therefore remain retained and may be reported as unmatched. The status DTO does not expose `reviewReason` or `exceptionAccepted`. A normal pickup approval updates its verdict to `VERIFIED` but preserves the server's original verification reasons/score. An approved exception can still be returned as `NEEDS_REVIEW`; the collector cannot infer approval details the API does not provide. Those details remain in the supervisor workflow. Previously terminal local records are not automatically reopened by this fix.

This app is the **collector surface**, not a supervisor approval console. Reviews and corrections happen in the main web/API supervisor workflow. Open-demo access is server-advertised and uses only the seeded collector role; it does not bypass device registration, evidence checks or server scope enforcement. There is no gallery evidence, background tracking, government API integration, or simulated scale hardware.

## Maestro and Physical Acceptance

Files are under `apps/collector/.maestro/`. They are executable navigation/assertion flows, **not a claim that device testing has been performed**. Use a real Android phone, a disposable seeded account, current route assignments at the actual test location, printed signed property QRs, and a real scale. Grant foreground camera/location permissions. Start in English. Do not run `clearState`, uninstall, or clear app data against unsynced evidence.

`01-login.yaml` remains the authenticated-mode flow. In open-demo, startup skips that flow: register the device if needed, then run the capture/restart/sync flows from the route screen. Also test a failed first `/me`, offline restart, and both server mode transitions; demo screens must not expose Login, sign-out or membership switching.

```sh
maestro test -e PHONE=+919999999999 -e OTP=123456 -e MEMBERSHIP_ID="$MEMBERSHIP_ID" -e STOP_ID="$STOP_ID" apps/collector/.maestro/01-login.yaml
```

Set `MEMBERSHIP_ID`, `STOP_ID` and `PROPERTY_CODE` to the actual seeded assignment before these commands. The example OTP is valid only if the API explicitly enables the development provider. It is not hardcoded in the app. Set airplane mode on the phone; on supported Android versions the test operator can use `adb shell cmd connectivity airplane-mode enable`. Then:

```sh
maestro test -e STOP_ID="$STOP_ID" -e PROPERTY_CODE="$PROPERTY_CODE" apps/collector/.maestro/02-offline-draft.yaml
```

The two-stream draft flow enters 4.200 wet / 1.800 dry, force-stops and reopens, then asserts persisted values. Set up those actual weights on the scale; do not use these fixture numbers as real-world measurements without weighing. Physically point the camera at the correct evidence **before each separate invocation**:

```sh
maestro test -e PHOTO_BUTTON=doorstep-photo apps/collector/.maestro/03-live-photo.yaml
maestro test -e PHOTO_BUTTON=scale-photo-WET apps/collector/.maestro/03-live-photo.yaml
maestro test -e PHOTO_BUTTON=scale-photo-DRY apps/collector/.maestro/03-live-photo.yaml
maestro test apps/collector/.maestro/04-save-restart.yaml
```

Restore connectivity physically (or `adb shell cmd connectivity airplane-mode disable` on supported devices), then:

```sh
maestro test apps/collector/.maestro/05-sync-review.yaml
maestro test apps/collector/.maestro/07-language.yaml
```

For a new identified stop, `06-weight-unavailable.yaml` selects the exception and enters a note. Capture distinct doorstep and exception evidence with `03-live-photo.yaml`, then use `04-save-restart.yaml`. A QR-only path should also be exercised physically; the draft flow uses the route-local code fallback to avoid pretending an automated camera scan is a real QR test.

Required manual acceptance beyond these flows:

1. Three real offline pickups, process kill and device reboot, reconnect, and supervisor review. Check SQLite rows and durable files survive; app uninstall/clear-data is intentionally outside that guarantee.
2. Kill after presign, after PUT, after confirm and after batch server commit. Confirm one server event per UUID and no re-upload of confirmed photos. Expire both a presigned PUT URL and an already-uploaded but unconfirmed five-minute reservation. On explicit confirmation expiry, verify the saved JPEG is re-uploaded under a new reservation while UUID, capture, confirmed peers and eventual idempotency key stay unchanged.
3. Reject a tampered QR, a code for another route/stop, stale route, zero/missing/overprecision weight, contamination without reason, and exception without note/photo. Every failure must preserve the draft or queued event.
4. Deny camera/GPS permission, disable location, test weak GPS accuracy and storage exhaustion, revoked devices, expired/rotating JWTs, multiple memberships and sign-out/re-login. Confirm membership A evidence is not shown or sent under membership B.
5. Return real server `NEEDS_REVIEW`, structured and unstructured 422 rejections, 409 originals and 429/5xx errors. Approve a normal pickup through the supervisor API, refresh collector verdicts, and verify `SYNCED` plus `VERIFIED`, including an event beyond the first page. Confirm diagnostics retain actual reasons; transport status must not be mistaken for verified pickup.
6. Inspect normalized server JPEG metadata/hash, object-storage private ACLs, duplicate-photo rejection, geofence enforcement and the resident receipt. These are server integration checks, not client-side promises.
7. Inspect English/Hindi at 360 and 390 px, large font/accessibility mode, sunlight/gloves and a low-memory phone. Measure battery, disk growth and 500-stop throughput on the actual network. No performance target is claimed without measurement.
