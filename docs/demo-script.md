# Ten-Minute Demo

## Purpose

Show an evidence trail from registry to offline capture, review, resident feedback, billing and ULB oversight. This is a **rehearsal script**, not a claim that a physical Android demonstration has already passed. Allow setup/rehearsal time outside the ten-minute presentation.

Say up front: "This is fictional Nagar demo data. The live test captures are at our test site. Offline evidence requires supervisor review. This system prepares records; it does not certify compliance or submit to government systems."

## Preflight Before Starting The Clock

1. Complete [README setup](../README.md#local-setup). Run API/web, Redis and the separate `pnpm --filter @swachh/api worker`. Use `STORAGE_DRIVER=local` for the verified storage path. Check health/readiness, one actual signed image read, and one upload/confirm from the presenting browser. A green readiness response does not check storage or Redis.
2. Keep `NODE_ENV=development`, `DEMO_MODE=true` and the seeded tenant's billing/compliance flags enabled. Export `NEXT_PUBLIC_DEMO_MODE=true` when starting Next if using role buttons; a root `.env` alone is not loaded by Next's package directory. Production builds intentionally hide those buttons. Phone/OTP login is the fallback.
3. Open separate web tabs for society admin, supervisor, resident and ULB admin. Log in just before rehearsal; tokens are memory-only and full reload signs out. Use sidebar navigation instead of replacing the page URL after login. Allow 60 seconds between OTP requests for the same identity and avoid hitting five requests/hour during repeated rehearsals.
4. Use the synthetic identities from the table below. Keep resource IDs from the UI/API responses in rehearsal notes: society, test properties, resident-linked property, collector, today's route/stops, new event UUIDs, complaint and invoice. UUIDs are not stable bookmarks across resets.
5. On a real Android phone, install a compatible SDK 54 client or native `in.swachhtrack.collector`, grant camera/foreground location permission, and set `EXPO_PUBLIC_API_URL` to the API host's LAN address. Set `API_PUBLIC_URL` (local storage) or `S3_PUBLIC_ENDPOINT` (S3) to a phone/browser-reachable address too. Reopen Expo after public environment changes.
6. **Fix the seed/site mismatch before capture:** default properties are fictional Pune-area coordinates. In a disposable demo database, create/update three test properties at the actual test location and link one to the demo resident. Use the society registry/API to create a fresh route for today's IST date with the intended collector, documented valid vendor and applicable schedules. Do not alter production locations, spoof GPS or expand the geofence to hide the mismatch.
7. For a short physical demo, prepare a route whose actual schedules require only the streams you will weigh. Seeded route stops list all four streams, and the app requires every scheduled stream for a normal pickup. Do not enter invented sanitary/special-care weights to get past this. If necessary, adjust test schedules through their full-body PATCH, then create a new dated route; existing routes do not rebuild themselves.
8. Sign in online and register the collector device, then fetch the new route before disabling networking. A seeded device consumes one of the two binding slots; revoke an obsolete demo device through the supervisor API if necessary. Verify the selected stops, printed signed QRs, unique six-digit codes and property coordinates. For a new demo day, create new dated routes; rerunning the completed seed does not refresh them.
9. Have a real scale, distinct weighed test material, printed QR and three distinct evidence scenes. Capture two real offline events immediately before the timed segment, leaving them queued; do not sync yet. The timed segment captures the third. Keep location services on while disabling Wi-Fi/mobile connectivity. Show the prequeued events as prepared, not newly captured during the presentation.
10. Prepare a harmless complaint image and a separate resolution image for browser upload, a permitted unbilled demo month, and the financial-year start containing seeded history. Prefer a completed month; the seed already has invoices for the preceding two months. If using the current month to show a newly reviewed pickup, wait until its scheduled window has ended and explicitly call the invoice a partial-observation demo draft. Already-generated invoices do not recalculate when new evidence arrives.

## Expected Results And Troubleshooting

- **Offline path:** `PENDING/SYNCING -> SYNCED` locally, `NEEDS_REVIEW` on server, then explicit reasoned supervisor approval to `VERIFIED` for a valid weighed event. Accepted exceptions remain non-verified. Never substitute immediate offline verification.
- **Geofence rejection:** inspect property coordinates vs real GPS and route assignment; do not override a hard rejection. Preserve its UUID/reasons and prepare a new valid test stop/event. Weak GPS accuracy is a review flag, not permission to fabricate coordinates.
- **No route today:** the seed is a one-time snapshot. Create today's route with active schedules and an in-date documented vendor/contractor, then refresh the cache online before capture.
- **Image unavailable:** check `API_PUBLIC_URL`/`S3_PUBLIC_ENDPOINT` reachability, matching content type and unexpired capability. Browser CORS matters for direct S3 PUT. Never rewrite a signed URL's host in the client.
- **No newly approved event in a list:** inspect pagination/filter scope and actual event ID. Supervisor list is a review queue, not all-status history. Do not present a different seeded event as the captured event.
- **Invoice conflict:** use the existing draft/issued invoice or a genuinely unbilled month. Invoice generation is unique per society/month; annual draft is unique per society/FY. Do not delete history to force a second generation.
- **Empty notifications:** the worker must mark in-app rows delivered; IST quiet hours can defer ordinary notifications. Email/WhatsApp/FCM are not evidence of delivery. Do not change database timestamps to simulate a real SLA breach.
- **Lost web login:** sign in again after reload; respect OTP cooldown. Do not store tokens in the console or bypass the API.

## Honest Fallback Without Android

If no phone is available or the preflight fails, keep the same ten-minute outline but replace 02:00-04:00 with an explanation of the collector queue code/tests and a **clearly labeled seeded** review example. Continue resident/complaint/billing/compliance/ULB workflows on their actual records. State: "The physical camera, GPS, airplane-mode and restart demonstration was not run. This is a web/backend demonstration, not offline field acceptance."

No Android/Maestro run or 500-queued-event benchmark is currently recorded. A rehearsed recording, unit test or synthetic review must never be relabeled as a successful physical-device test. Record actual results separately using [acceptance](acceptance.md); do not publish temporary development tunnel URLs as deployment addresses.
